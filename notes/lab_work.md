# Java Streams — лабораторная

## Цель

На коде понять, когда Stream API делает обработку коллекций понятнее, почему конвейер ленивый, как собирать данные через collectors и почему parallelStream не является автоматическим ускорителем.

## Карта понятий

    Источник данных
            │ stream()
            ▼
    Промежуточные операции
            │ filter / map / distinct
            ▼
    Терминальная операция
            │ toList / count / collect
            ▼
    Результат

- Stream — одноразовый конвейер обработки элементов, не коллекция.
- Intermediate operation — ленивый шаг, например filter или map.
- Terminal operation — запуск конвейера: toList, count, collect.
- Collector — правило сборки stream в итоговую структуру.
- parallelStream — stream, который использует common pool для частей конвейера.

## 1. Фильтрация и преобразование без ручного цикла

Код: [Lab_Main.java](../src/main/java/org/Lab_Main.java). Четыре заказа проходят через два независимых конвейера.

| Задача | Конвейер |
| --- | --- |
| Сумма оплаченных заказов | filter → mapToInt → sum |
| Клиенты с заказом от 100 | filter → map → distinct → toList |

Stream описывает результат, а не временные переменные и механику обхода.

### Мои выводы

> Stream не отменяет логику — он делает порядок преобразований видимым.

> toList завершает конвейер и возвращает неизменяемый список.

## 2. Ленивость и terminal operation

Код: [LazyPipeline_Main.java](../src/main/java/org/LazyPipeline_Main.java).

| Момент | Что происходит |
| --- | --- |
| Создали stream и написали filter | Ничего не обходится |
| Вызвали limit(2).toList() | Конвейер читает элементы |
| Получили два результата | Источник дальше не читается |

peek здесь нужен только для диагностического вывода, а не для бизнес-логики.

### Мои выводы

> Промежуточная операция описывает работу, но не запускает её.

> limit вместе с ленивостью может остановить обработку раньше конца источника.

## 4. parallelStream и CPU-bound работа

Код: [ParallelStream_Main.java](../src/main/java/org/ParallelStream_Main.java). Оба варианта считают простые числа до миллиона.

| Вариант | Что сравнивать |
| --- | --- |
| Обычный stream | Базовое последовательное время |
| parallelStream | Время с учётом common pool и ядер |

Параллельный stream может выиграть на тяжёлой CPU-задаче, но проиграть из-за overhead на маленькой коллекции.

### Мои выводы

> Больше потоков не означает больше ядер.

> parallelStream нельзя включать на всякий случай.

## 5. Границы Stream API

| Ситуация | Подход |
| --- | --- |
| Короткая обработка коллекции | Stream делает цепочку яснее |
| Сложное ветвление и состояние | Обычный цикл может читаться лучше |
| Ресурсный stream | Использовать try-with-resources |
| Параллельная CPU-обработка | Сначала измерить |

Stream одноразовый: после terminal operation его нельзя использовать повторно.
